# 热更测试 Skill

## 🔒 上下文隔离机制

**`@热更测试` 遵循后端通用的 `@` 指令上下文隔离规则：**
- 后端检测到 `@` 前缀 → 仅发送 **system prompt + 当前消息**（含上传文件解析块）
- 这是后端对所有 `@` 指令（现有及未来新增）的通用处理，热更测试无需特殊配置
- 不携带任何历史对话记录，每次 `@热更测试` 都是干净的独立会话
- **好处**：防止上下文过长导致 AI 回复超时或失败；减少 token 消耗
- **后续消息**（如回复行号 "20"）不以 `@` 开头 → 正常携带完整历史上下文

## ⛔ 触发条件（严格限制）

**仅在以下情况激活此 Skill：**
- 用户消息**以 `@热更测试` 或 `@hot-update-test` 开头**

**以下情况绝对不要激活：**
- 用户消息中普通提及「热更测试」「hot update test」等关键词但**没有 `@` 前缀**
- 用户在讨论热更测试相关问题、排查 bug、查看日志时
- 任何不以 `@热更测试` 或 `@hot-update-test` 开头的消息

**判断逻辑**：
```
if 用户消息.strip().startswith('@热更测试') or 用户消息.strip().startswith('@hot-update-test'):
    ✅ 激活 Skill
else:
    ❌ 不激活，当作普通对话处理
```

**重复触发规则（强制）**：每次用户输入 `@热更测试` 或 `@hot-update-test` **作为消息开头**时，**必须无条件从头开始**：
- ❌ 禁止复用之前对话中的项目名、文档、方案号、行号、测试结果
- ❌ 禁止根据上下文推断用户要测哪个项目或哪一行
- ✅ 必须像首次对话一样，从步骤1开始重新收集项目名称和需求文档
- ✅ 即使用户上一轮刚测过同一个项目，本轮也必须重新确认

> 📌 此规则**仅当用户消息以 @热更测试 开头时触发**。用户回复行号（如 "4"）或「全部」时不触发重置，可正常使用历史上下文中的 project 和 file_id。

## 概述

此 Skill 用于对 AB 实验热更调参进行自动化配置比对测试。用户需要提供两个必要信息：**项目名称**和 **AB 实验需求文档（Excel）**。

## 执行流程

### 步骤 0：重置上下文（仅在 @热更测试 触发时执行）

**触发条件**：用户消息以 `@热更测试` 或 `@hot-update-test` 开头。

**强制规则**：
```
用户本轮消息 = "@热更测试"（无项目名、无文档）
  → 之前对话中即使上传过10个文档、说过100次项目名，全部作废
  → 必须回复：请提供项目名称 + 上传 AB 实验需求文档
  → 禁止直接跳到步骤2展示文档解析结果
```

- 🗑️ 历史上下文中的项目名、文档、方案号、行号、测试报告 —— **全部视为不存在**
- 🆕 只看用户**本轮 @热更测试 消息中**附带的内容
- ❌ 绝对禁止：「根据之前上传的文档...」「沿用上一轮...」「上次测试的...」
- ❌ 绝对禁止：用户只发了 `@热更测试` 三个字，却展示了文档解析结果

> ⚠️ **重要**：此重置规则**仅在用户消息以 @热更测试 开头时生效**。
> 一旦进入步骤 2（展示方案行列表），后续用户回复行号等操作**不再触发重置**，
> 此时可以正常使用对话历史中的 project、file_id 等信息。

---

### 步骤 1：检查必要信息（缺一不可）

**仅在首次 @热更测试 触发时检查本轮消息。即使历史上下文中有文档，只要本轮没重新上传或指定，就视为缺少。**

热更测试需要以下**两个必要信息**，**缺一不可**：

| 序号 | 必要信息 | 说明 | 示例 |
|------|---------|------|------|
| ① | **项目名称** | 中文名称或内部标识 | `iOS方块-AB3.5` → `ios_blcokblast_ab3.5_orth` |
| ② | **需求文档** | AB 实验 Excel 文件（.xlsx） | `AB实验第217期RV-策略平台热更.xlsx` |
| (可选) | 指定行号 | 默认第 4 行（第一行数据） | `第4行` |

**检查逻辑（严格按顺序执行）：**

```
用户输入 `@热更测试`
  │
  ├─ ①② 都缺？→ ❌ 回复：
  │   ```
  │   📋 热更测试需要提供以下信息：
  │   1️⃣ 提供项目名称
  │   2️⃣ 提供 AB 实验需求文档（.xlsx 格式）
  │   （列出所有支持的项目名称）
  │   ```
  │
  ├─ 缺项目名（有文档）？→ ❌ 列出项目列表让用户选择
  │
  ├─ 缺文档（有项目名）？→ ❌ 回复：「请上传 AB 实验需求 Excel 文档（.xlsx格式）」
  │
  └─ ①② 都具备 → ✅ 进入步骤 2，先解析文档展示所有方案行
```

**回复模板：**

- 两者都缺时：列出必需信息（1.项目名称 2.需求文档）+ 所有可用项目
- 缺少项目名时：列出所有可用项目供选择
- 缺少文档时：「请上传 AB 实验需求 Excel 文档（.xlsx格式）。」
- 两者都有时：**进入步骤 2，先解析文档列出所有方案行让用户确认**

### 步骤 2：解析文档，展示所有方案行（必须执行）

当项目名和文档都具备后，**必须先解析 Excel 文档的所有数据行**，列出每一行的方案信息供用户确认，**不要跳过此步骤直接执行**。

**Excel 文档结构**（第 3 行为表头，第 4 行起为数据行）：

| 列 | 表头 | 说明 |
|----|------|------|
| A | 原始方案编号 | **新方案号** — 本次热更的目标方案（如 `rv217601`） |
| B | 广告类型 | 激励/插屏等 |
| C | 方案概述 | 包含**底板方案号**（如 `【底板】rv176685`） |
| D | abtest | AB 测试标识 |
| E | 技术 | 技术说明 |
| F | 方案细节 | 详细的方案变更描述 |

**解析规则：**

1. **新方案号（右侧）**：取 A 列的 `原始方案编号`
2. **底板方案号（左侧）**：从 C 列 `方案概述` 文本中提取：
   - 优先匹配 `【底板】` 后面的 `rv*` 或 `fs*` 方案号
   - 其次匹配 `基于` 后面的第一个 `rv*`/`fs*` 方案号
   - 所有方案号格式：`rv` 或 `fs` 开头 + 数字（如 `rv176685`、`fs1011`）
3. **前向填充（Forward Fill）** — 逐行解析时从第 4 行往后扫描，**工具执行时自动向上追溯直到找到有效值为止**：
   - 如果当前行 **A 列为空**（无新方案号）→ 向上查找**前一行的新方案号**，直到找到为止
   - 如果当前行 **C 列提取不到底板方案号** → 向上查找**前一行的底板方案号**，直到找到为止
   - 如果当前行 **C 列概述为空或仅含底板声明**（如只有「底板」二字）→ 向上查找**前一行的完整概述内容**，并从中提取底板方案号
   - 首次遇到空值且向上追溯到第4行仍无有效值 → 标记为「（无）」并报错

**展示格式（固定模板）：**

解析完文档后，必须用以下格式按块列出**所有数据行**：

```
📋 文档解析结果 — 共 N 行方案：

──────────────────────────────
第 4 行
  新方案号：rv217601
  原方案号：rv176685
  新方案修改概述：重试逻辑+底价设置
──────────────────────────────
第 5 行
  新方案号：rv217602
  原方案号：rv159610
  新方案修改概述：频次控制调整
──────────────────────────────

请确认要测试第几行？直接回复行号（如 4），或回复「全部」测试所有行。
```

**展示后，等待用户确认行号，不要自动执行测试。**

> 📌 **进入步骤 2 后，project 和 file_id 已确定。后续用户回复行号时，从对话历史中取回这两个参数即可。**

### 步骤 3：根据用户确认的行号执行配置比对

**参数来源（重要！）**：
- `row_number` — 用户本轮回复的行号（如 4）
- `project` — **从对话历史中提取**（步骤 1 中已确认的项目内部标识）
- `file_id` — **从对话历史中提取**（步骤 2 文档解析结果中的 FILE_ID）

> ❌ 禁止因为"只看本轮消息"而忽略历史中的 project 和 file_id
> ✅ 用户回复行号时（消息不以 @热更测试 开头），不会触发步骤 0 重置，历史上下文有效

**如果是单个行号**：先简短确认（如"正在执行第4行热更测试..."），然后附加工具调用：`[TOOL_CALL:hot_update_test]{"project":"<从历史中提取>","file_id":"<从历史中提取>","row_number":4}[/TOOL_CALL]`

**如果用户回复「全部」**：先简短确认（如"正在执行全部 N 行热更测试..."），然后对每一行依次附加工具调用，每条独占一行：
```
[TOOL_CALL:hot_update_test]{"project":"xxx","file_id":"xxx","row_number":4}[/TOOL_CALL]
[TOOL_CALL:hot_update_test]{"project":"xxx","file_id":"xxx","row_number":5}[/TOOL_CALL]
...
```工具将自动执行以下操作：

**3.1 Playwright 无痕登录，获取 Token**
- 通过 Playwright 无痕浏览器打开前端登录页
- 自动填入用户名密码（auto_user / auto_user）
- 登录成功后从 `localStorage` 提取 `admin_token`
- 立即关闭浏览器，后续操作通过 HTTP API 完成

**3.2 调用方案列表 API**
```
GET /api/operate_tool/git_config_diff/get_adwaynum_file/
  ?project_name={project}&business_v=&timeslot=left_time_slot_0
```
- 后端自动执行 git pull 同步配置仓库
- 返回该项目的所有方案文件列表（如 `["zy--rv176685", "zy--rv217601", ...]`）

**3.3 匹配方案号**
- 在返回的方案列表中，通过子串匹配找到左右方案号对应的**完整方案路径**
- 左侧（底板）：用 `left_scheme` 匹配 → 得到如 `zy--rv176685`
- 右侧（新方案）：用 `right_scheme` 匹配 → 得到如 `zy--rv217615`
- ⚠️ 如果匹配不到 → 抛出明确错误：「方案号 rvxxx 在项目 xxx 的方案列表中未找到」

**3.4 调用方案 JSON API**
```
GET /api/operate_tool/git_config_diff/get_adwaynum_json_2/
  ?project_name={project}&business_v=&adwaynum={matched_name}&timeslot=left_time_slot_0
```
- 分别获取左右两侧方案的完整 JSON 配置
- 返回格式：`{"data": {"adwaynum_json": {...}}}`

**3.5 JSON 深度对比**
- 比较两侧 JSON 的 Key 结构（是否有增删的字段）
- 比较共同 Key 的 Value 值（是否有变更）
- 列出所有差异项

**3.6 异常处理**
- 登录失败 → 提示「自动登录失败，请检查 auto_user 账号是否正常」
- 方案号在列表中找不到 → 提示「方案号 `rvxxx` 未找到（列表共 N 个方案），请���认方案号正确」
- API 超时（60秒）→ 提示「方案列表/json API 超时，请检查后端服务」
- JSON 获取失败 → 指出是左侧还是右侧失败，附带 API 返回的错误信息

### 步骤 4：AI 网关生成逐条验证报告

**工具执行完成后，后端自动完成以下流程（无需 AI 助手干预）：**

1. **提取差异数据**：从两个方案的 JSON 对比结果中提取所有功能差异项（old→new 值）
2. **提取文档内容**：从上传的 Excel 文档中提取该行的「方案概述」和「方案细节」
3. **构建隔离上下文**：使用专用的报告生成 System Prompt（不含 TOOL_CALL 指令），将差异列表 + 文档内容组合为一次独立的 AI 网关调用
4. **AI 逐条分析**：AI 网关根据文档中描述的预期改动，逐条对比差异：
   - ✅ 匹配到文档描述 → 测试通过
   - ❓ 无法匹配 → 待人工确认
   - ⚠️ 纯底板方案出现差异 → 标记异常
5. **输出报告**：生成结构化的验证报告，包含基本信息表、adwaynum忽略说明、逐条验证结果、测试结论

> ⚠️ **重要**：报告生成使用隔离的 AI 上下文（不包含主对话的 System Prompt），
> 避免 TOOL_CALL 指令干扰导致 AI 误判。报告由 AI 直接分析生成，不使用代码级匹配逻辑。
> 当 AI 网关不可用时，降级为基础数据摘要（不含智能匹配）。

**AI 助手收到报告后直接展示即可，不需要再做额外的分析或总结。**

## 执行注意事项

1. **方案号格式**：严格匹配 `rv` 或 `fs` 开头 + 纯数字（如 `rv176685`、`fs1011`），不匹配纯数字（如 `124046`）这类 adunit ID
2. **底板识别优先级**：`【底板】rv*` > `基于rv*` > C 列中第一个 `rv*`/`fs*`
3. **多底板情况**：如果方案概述中引用了多个底板方案号，默认取第一个（最近的底板）
4. **无痕登录**：Playwright 仅用于登录获取 token，之后立即关闭浏览器，API 调用通过 requests 库完成
5. **超时处理**：API 请求 60 秒超时，超时后给出明确错误提示
6. **方案匹配**：在方案列表中使用子串匹配（ignore case），因此原始方案号 `rv176685` 可以匹配到列表中的 `zy--rv176685` 等路径
7. **Token 管理**：每次执行都重新登录获取新 token，不缓存旧 token

## 常见故障排查

| 现象 | 原因 | 解决方法 |
|------|------|---------|
| 登录后未获取到 token | auto_user 账号异常或密码错误 | 检查 auto_user 账号状态是否正常 |
| 方案列表 API 返回空 | git 仓库未同步或项目目录不存在 | 检查后端 git 仓库状态；确认项目名称正确 |
| 方案号在列表中匹配不到 | 方案号不存在或格式不匹配 | 确认方案号正确；检查列表返回的方案名格式 |
| 方案 JSON API 返回错误 | 方案路径无效或 JSON 解析失败 | 确认列表匹配到的方案路径正确有效 |
| API 调用超时（60秒） | 后端服务负载高或 git pull 卡住 | 检查后端服务器状态；重试 |
