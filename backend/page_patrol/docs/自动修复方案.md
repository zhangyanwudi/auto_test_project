# 页面巡检：定位失效自动修复方案（待确认）

> 状态：设计稿，未实现。确认后再按第 8 节的顺序执行。

## 1. 目标与范围

- **做**：case 回放时因「定位失效」失败（找不到文字、字段、下拉选项、列、行、按钮，或元素超时），由 AI 根据失败现场修正模块 JSON 中对应步骤的定位字段，然后重新回放整个 case，直到成功或达到上限，失败时输出原因。
- **不做**：
  - 校验失败（订单状态、达人类型、产品组合、「提交成功」未出现等）；
  - 提交之后发生的任何失败；
  - 登录失效、网络、环境问题；
  - 修改录入值（`data`、`value`）、`kind`、`inputs`、`verify`、页面结构。
- **写回**：修复结果只存在内存与报告文件中。模块 JSON 只有在人工执行 `apply-repair` 确认后才写回，写回前自动备份。

## 2. 现有流程（不变的部分）

```
task_file/page_patrol_task.py case --case X.py [--order_type]
  └ _load_case → mod.build(base_json)            # 内存中的 data，补 run/关闭提交
  └ _run_data → patrol_core.validate(data)       # 静态检查
  └ patrol_core.execute(data, post_check)        # 浏览器回放，返回 {ok, error, screenshot, payload}
  └ 成功且 mod.CHAIN_NEXT → 写缓存 → run_case(下一个 case, chained=True)
```

`explore` 子命令（AI 探索生成 JSON）保持原样，自动修复不调用它。

## 3. 新流程

```
case --repair
  └ run_with_repair(mod, data)
       for attempt in 1..MAX_ATTEMPTS:
         rep = patrol_core.execute(data, post_check, want_snapshot=True)
         ├ ok                              → 结束：成功（记录尝试次数）
         ├ kind != 'locate'                → 结束：失败，原样报告
         ├ rep.after_submit == True        → 结束：失败，禁止重试，报告草稿风险
         ├ 超过时间预算                     → 结束：失败，报告超时
         └ patch = propose_patch(rep.snapshot, failed_step)
             ├ 无补丁 / give_up            → 结束：失败，报告 AI 结论
             ├ 补丁重复（同一内容已尝试）    → 结束：失败，报告
             ├ validate_patch 不通过       → 结束：失败，报告
             └ data = apply_patch(data, patch)   # 只改内存副本
  └ 写 repair_report.json（每次尝试：错误、快照路径、补丁、结果）
  └ 若成功：打印「待确认写回」，不写模块 JSON

apply-repair --report repair_report.json     # 人工确认后执行
  └ 检查报告中的原模块 JSON 未被改动（哈希比对）
  └ 备份为 <模块>.json.bak.<时间戳>
  └ 写入补丁后的模块 JSON，再执行 validate_module
```

## 4. 函数划分

### 4.1 新增文件 `page_patrol/repair.py`

| 函数 | 职责 |
|---|---|
| `classify_error(exc_or_msg, step_ctx)` | 返回 `locate` / `verify` / `env` / `post_check` |
| `build_snapshot(page, failed_step, error)` | 采集失败现场：截图路径、可见文字（截断 2000 字）、可交互元素清单（复用 `observe_page`）、失败步骤 JSON、错误文本 |
| `propose_patch(snapshot, case_context)` | 调用 AI（复用 `runner._call_ai`），返回补丁列表或 `give_up` |
| `validate_patch(patch, data)` | 白名单字段、路径存在、补丁后 `validate_module` 通过 |
| `apply_patch(data, patch)` | 深拷贝后修改，返回新的 data，不改磁盘 |
| `run_with_repair(mod, data, upload, headless)` | 修复循环（第 5 节停止条件） |
| `write_report(path, record)` | 写 `repair_report.json` |
| `apply_report(report_path)` | 人工确认后写回模块 JSON，含备份与哈希校验 |

### 4.2 修改 `apps/case_govern/case_runner/explorer.py`

- `ExploreError` 增加属性 `kind`（`locate` / `verify` / `env`，默认 `None`）。
- 各定位抛错处显式标注 `kind='locate'`：`_click_by_label`、`_fill_by_label`、`_select_option`、`_table_cell`、`_click_row`、`_recognize`、`_wait_filled`、`replay_page` 的 anchor 检查。
- `_verify_text`、`_verify_row` 标注 `kind='verify'`。
- 不改变现有报错文本，只补充属性，保证现有调用不受影响。

### 4.3 修改 `page_patrol/patrol_core.py`

- `execute(..., want_snapshot=False)`：失败时若 `want_snapshot` 为真，调用 `repair.build_snapshot`。
- 在回放 `click` 步骤前检测 label 为「提交审核」（或 case 指定的写入边界），设置 `reached_submit=True`；返回值增加 `after_submit`、`kind`、`failed_step_index`、`snapshot`。
- 返回值结构保持向后兼容：原有键不变，只新增键。

### 4.4 修改 `task_file/page_patrol_task.py`

- `case` 子命令增加 `--repair`（默认关闭，显式开启才走修复流程）。
- 新增子命令 `apply-repair --report <path>`。
- 链式调用时，修复只作用于当前 case；上一个 case 失败则不触发下一个。

### 4.5 修改 case 文件（可选）

- 声明 `WRITE_BOUNDARY_LABEL = '提交审核'`（订单 case）或 `'保存'`（上传 case）。未声明时默认按「提交类」关键字保守处理。

## 5. 补丁格式

AI 只允许输出如下结构（JSON）：

```json
{
  "patches": [
    {
      "page": "达人列表",
      "operation": "创建订单",
      "step_index": 3,
      "path": ["steps", 3, "label"],
      "old": "请选择平台",
      "new": "请选择平台"
    }
  ],
  "reason": "页面中平台下拉的占位文字已改为「请选择渠道」",
  "give_up": false
}
```

**白名单字段**（`path` 最后一段必须是其一）：

- `label`、`column`、`selector`、`nth`、`row`

**禁止**：

- 修改 `value`、`data`、`text`（录入值）；
- 修改 `kind`、`inputs`、`verify`、`verify_row`、`anchor`、`enter`、`goals`、`children`；
- 增删步骤、改变步骤顺序、修改 `action` 类型；
- 跨页面或跨操作修改。

**校验规则**：

- `old` 必须与当前 JSON 中该路径的值完全一致，否则拒绝（防止 AI 基于过期信息修改）；
- 应用后整体通过 `validate_module`；
- 单次最多 3 条补丁。

## 6. 停止条件

| 条件 | 结果 |
|---|---|
| 回放成功（含 post_check） | 成功，停止 |
| 失败 `kind != locate` | 停止，原样报告，不修复 |
| 失败发生在写入边界之后（`after_submit`） | 停止，禁止重试，报告 |
| 达到 `MAX_ATTEMPTS = 3` | 停止，报告所有尝试 |
| 累计耗时超过 `BUDGET = 10 分钟` | 停止，报告超时 |
| AI 返回 `give_up` 或无补丁 | 停止，报告 AI 结论 |
| 补丁与之前某次完全相同 | 停止，报告「修复无进展」 |
| `validate_patch` 失败 | 停止，报告补丁被拒绝的原因 |

## 7. 幂等与副作用（关键风险）

**问题**：回放在「提交前」也会产生副作用。订单 case 的右下角「创建订单」会生成草稿（列表中为「沟通阶段」）。重试会再生成一个草稿，留下孤儿草稿。

**策略**：

1. 写入边界前的定位失败：允许重试，但报告中必须列出本次尝试产生的草稿数量，由人工清理。
2. 写入边界之后：禁止重试。
3. 每次重试前，先检查 `last_order` 缓存与订单列表中是否已存在该达人的「提审阶段」订单；若已存在，直接停止并报告，不再提交。
4. 上传 case 的「保存」之后同理：保存成功后不重试。

**无法完全避免的情况**：草稿阶段的孤儿数据只能人工清理，自动化无法可靠识别。这一点需要你确认是否接受。

## 8. 执行顺序（确认后）

1. `ExploreError.kind` 与定位点标注（纯增加属性，不改行为）。
2. `patrol_core.execute` 返回新增字段，并增加写入边界检测。
3. 新增 `page_patrol/repair.py`，先实现 `classify_error`、`build_snapshot`、`validate_patch`、`apply_patch`，并单测（使用临时 JSON，不启动浏览器）。
4. 实现 `propose_patch`，用一个已知失效的定位样本（例如故意把 label 改成错误值）验证 AI 能给出正确补丁。
5. 实现 `run_with_repair` 与 `case --repair`，先只用 `--dry-run` 外的故意错误 JSON 副本验证循环与停止条件。
6. 实现 `apply-repair`，并验证备份与哈希校验。
7. 人工在有界面模式下各跑一次成功路径与失败路径。

## 9. 测试计划

- **单元测试**（不启动浏览器）：白名单拒绝、`old` 不匹配拒绝、补丁重复检测、`after_submit` 禁止重试、预算超时。
- **集成测试**（浏览器）：
  - 将一个 label 改成错误值，确认修复成功并输出报告；
  - 将 `data` 中的录入值改错，确认不触发修复（因为不是定位失效）；
  - 模拟写入边界之后失败，确认不重试。
- **回归**：未开启 `--repair` 时，行为与现在完全一致。

## 10. 已确认的决定

1. `MAX_ATTEMPTS = 3`，时间预算 10 分钟。
2. 接受写入边界前失败可能留下草稿，需人工清理。
3. 写回采用独立命令 `apply-repair`。
4. 第一阶段只覆盖「订单履约-创建订单」。
5. AI 调用沿用 `ai_helper` 配置，修复使用视觉模型 `explore_model`（`qwen3.6-plus`，经 `_call_ai_vision` 调用）。
